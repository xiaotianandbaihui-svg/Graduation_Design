# 跳跃：宏配置＋足端逆解＋MPU9250落地估计

只需要修改 `jump.h` 顶部的宏，不再传Jump_Config，也不再对外暴露每个动作阶段。

## 1. 填宏

- `JUMP_GEOMETRY`：L1~L5，mm。
- `JUMP_SERVO_IDS`：左AB、左ED、右AB、右ED的四个舵机编号。
- `JUMP_OFFSET_DEG`、`JUMP_DIRECTION`：安装换算，`舵机角 = offset + direction * 几何角`。
- `JUMP_MIN_DEG`、`JUMP_MAX_DEG`：四个舵机安装后的允许指令角度。
- `JUMP_X_MM`、`JUMP_LOW_MM`、`JUMP_HIGH_MM`：足端前后位置、最低/最高可用腿高。
- `JUMP_MID_MM`：落地准备的中间腿高，默认取最低与最高的平均值，可自行修改。
- `JUMP_BUFFER_MM`：触地后屈腿的终点，必须实际填写，满足`LOW < BUFFER < MID < HIGH`，不能直接收至最短。
- `JUMP_BUFFER_MS`：屈腿计划用时，默认160ms仅为调试初值。
- `JUMP_BUFFER_MAX_MM_S`：腿高指令速度上限，默认150mm/s仅为调试初值；过快时自动延长屈腿用时。
- `JUMP_PREP_DELAY_MS`：检测腾空并收腿后，等多久再放到中间腿高，默认80ms只是调试初值。
- 下蹲时间、触地判定超时、采样间隔及离地/落地阈值也集中在该文件中。

NaN和direction=0是未填写标记，不是实物参数。最低/最高应为已验证的可用高度，不要填完全折叠或伸直的死点。其余时间和阈值都是调试初值，需要实测调整。

安装例子：AB几何角130°对应舵机90°，同向转动则offset=-40°、direction=+1；反向则offset=220°、direction=-1。四个舵机分别确定，不能用这个例子代替标定。

## 2. Get_Angles(x, y, angle)

```c
float angle[4];
if (Get_Angles(0.0f, 160.0f, angle)) {
    /* angle[0]：左AB舵机指令角
       angle[1]：左ED舵机指令角
       angle[2]：右AB舵机指令角
       angle[3]：右ED舵机指令角 */
}
```

输入是两腿共用的局部足端坐标，mm；输出为安装换算后的舵机角度，度。沿用两舵机轴中点为原点、+x向右、+y向下、张开姿态，两腿杆长相同。函数只计算，成功返回1、失败返回0且不改输出。四个数组元素按逻辑关节顺序排列，实际PWM编号由JUMP_SERVO_IDS映射。

## 3. 跳跃调用

先用原程序完成舵机、MPU和毫秒时基初始化，检查初始化成功；不要在每次跳跃时重新初始化。加入原 `leg_ik.c`、`servo.c`、`mpu9250_simple.c` 及其头文件、板级IIC/延时实现。

```c
/* 按键按下沿调用一次。立即下发最低腿高目标。 */
int8_t state = Jump_Start(now_ms);

/* 原有主循环中每1~5ms调用，内部每JUMP_SAMPLE_MS至多读一次加速度。 */
state = Jump_Update(now_ms);
if (state == JUMP_LANDED) {
    /* 已估计触地，且屈腿指令轨迹已发完，可以协调后续控制。
       不代表舵机实际跟踪到位，也不代表机身已经站稳。 */
    Jump_Stop(); /* 清除结果，让本事件只处理一次，不改变已发出的舵机目标 */
}
```

以上是不同调用位置的片段；不要在每次循环都调用Start。返回值只有：`JUMP_IDLE`空闲、`JUMP_RUNNING`执行中、`JUMP_LANDED`估计触地且屈腿指令轨迹完成、`JUMP_ERROR`失败。与上一版不同，正常触地的那一次调用仍返回RUNNING，后续必须继续调用Update来完成屈腿。结果会保留，直到重新Start或Stop。

执行顺序：

```text
最低目标 → 等待下蹲 → 最高目标 → 检测到连续低g → 最低目标收腿
                                                     ↓
                                    等待JUMP_PREP_DELAY_MS后放到中间高度
                                                     ↓
                                 估计触地 → 平滑屈腿到BUFFER高度 → 返回JUMP_LANDED
```

起跳和空中动作仍直接切换目标，触地后的屈腿改为平滑插值，不自动恢复站姿。每次屈腿更新都重新进行逆解和角度范围检查；最终保持BUFFER目标，保留距LOW的余量。等待期间不调用Delay，原控制循环可继续，但其他调腿任务不能同时覆盖这四路目标。同一IIC总线及舵机输出应由同一执行上下文访问。原Servo_SetAngle逐路写入，不是四路原子提交。

屈腿轨迹采用`y = MID + (BUFFER-MID)*(10u^3-15u^4+6u^5)`，其中u从0增加到1。计划曲线的起止速度、加速度均为0；触地判定那一刻不改变原中间高度目标。其峰值速度为`1.875*(MID-BUFFER)/T`，代码据此在速度过快时自动增大T。

例如仅作计算演示：MID=160mm、BUFFER=140mm、计划160ms、速度上限150mm/s，则用时会自动延长到至少250ms。并不是越慢就越能缓冲：太慢可能继续硬顶，太快可能使支撑不足。现有代码没有根据力或机身竖直速度闭环优化这条曲线。

每次有效调用最多推进一个采样周期的轨迹，即使调度迟到，也不会一次补发积累的位移；实际用时可能因此延长。速度上限约束的是足端y目标，不是舵机实际角速度或接地力。曲线从上次中间目标开始，尚无舵机实际位置反馈。触地后的轨迹用时独立计算，不会被原触地判定超时截断。

原始加速度在弹道上升和下降时都可能接近0g，不能据此知道最高点。这里按可调延时准备落地，不是精确检测“开始下落”。延时要兼顾实际飞行时间和舵机伸腿所需时间，使中间姿态能在触地前建立；若要准确识别下降阶段，需要额外的高度或竖直速度估计。

若在放到中间高度之前就出现连续触地迹象，代码先等待判据确认，不继续放长；确认早落地后保持最低目标。若只是短暂干扰、随后恢复低g，则继续执行中间高度准备。被忽略时间窗口内的早触地无法及时识别。

## 4. 为什么不只看az

机身倾斜时，静止状态下az也可能接近0，容易被误认为失重。因此代码使用未做重力补偿的原始三轴值：

```c
a_g = sqrtf(ax*ax + ay*ay + az*az) / JUMP_ACCEL_LSB_PER_G;
```

目前MPU初始化为±2g、200Hz，对应16384 LSB/g；内部浮点求平方，避免int16乘法溢出。若修改量程，必须同步修改比例：±4g为8192、±8g为4096、±16g为2048。提高量程还要同步检查原姿态算法使用的加速度比例。

默认过程：蹬伸至少40ms后，连续3次小于0.35g，估计已腾空并收腿；80ms后下发中间腿高目标。每次空中改变腿高目标后重新忽略60ms落地判据，以减少动作干扰；之后连续4次大于0.8g，估计已恢复地面支撑并启动平滑屈腿。忽略时间会延迟实际触地检测，需要按实测调整。落地不强求大于2g的冲击峰值，因此可包含较软的触地。启动后1500ms内仍未确认触地则报错，不把超时当作成功落地；已开始的屈腿轨迹不受此超时限制。

Update再快也不会在同一个采样间隔内反复计数；采样间隔超过设定值的2倍会清空连续计数。样本数宏取1~255，采样间隔须大于0。MPU9250_ReadAccel成功表示通信成功，现有驱动没有提供数据就绪时间戳；应确保传感器正常刷新，采样间隔与其输出频率匹配。不要把一个缓存旧样本反复当作新数据。

## 5. 宏接口与边界

```c
#define JUMP_READ_ACCEL(raw)      MPU9250_ReadAccel(raw)
#define JUMP_WRITE_SERVO(id, deg) (Servo_SetAngle((id), (deg)) == SERVO_OK)
```

两个接口均约定非0成功。更换驱动时只需修改这两个宏；如果改为读取缓存，返回成功必须表示确实取得了本周期有效的新样本。

读取失败不会当作0g；逆解失败、角度越界或触地判定超时都会返回ERROR并停止后续目标切换。触地后执行的是预设位置轨迹，该阶段不再用加速度改变屈腿速度。Cancel/ERROR保留已经发出的目标，不等于舵机立即停住或断电。

这是IMU落地估计，不是可靠接触测量：空中收腿、放腿、旋转和振动仍可能误判，极短或低高度跳跃也可能检测不到低g。触地后检测才会发生，不能消除第一下落地冲击。平滑位置指令只能减少指令本身的突变，不能保证实际卸力或减小接地力峰值；它不是VMC或力控。要控制实物冲击仍需机械弹性和阻尼、合适的接地姿态，并结合实测载荷调整。本模块无法判断左右轮是否都接地。测试冲击峰值时要留意当前±2g量程可能饱和。
